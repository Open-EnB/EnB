# Earth & Beyond client: C++ reconstruction

Rebuild of Westwood's E&B `client.exe` (retail, SHA-256 `249f8524…51c4`, built with VC6 SP4)
in its original C++. Import EA's published Westwood code where the client contains it;
reverse engineer the rest. Windows; shell is Git Bash (`/c/...` paths) or PowerShell.

## Start here (do this, don't re-derive)
1. Read the newest entry of `docs/progress.md` (log, decisions, open questions).
2. Read `docs/workflow.md` before touching libraries: the fix loop and **known traps** (§3.0 for
   everyone, then the subsections for your kind of work).
3. Builder subagents start from `docs/builders.md`: the startup set per builder kind, the rules,
   the report format and which model runs what (D72).
   Coordinators pace launches and the drain with the `coordinator-pacing` skill (usage, host memory,
   HEAD's health, the launch allowance, one command per heartbeat).
4. Index of everything else: `docs/README.md`. Tools: `tools/re/README.md`, `tools/vc6/README.md`,
   `tools/harness/README.md`. Do not read whole docs "to familiarize"; use `grep -n '^#'` and open
   the section you need.

## Hard rules
- **The git tree is authoritative.** The EA-derived libraries are plain source since the freeze
  (D211); `C:\EnBDevelopment\EA` is reference only.
- **Client wins**: where client.exe's names disagree with `docs/conventions.md`, use the
  client's and record the case in conventions.md.
- Verify before keeping a fix: compare sets of `(file, address)` pairs before/after
  (`tools/vc6/pairs_cmp.py`), not totals. No unexplained losses (D240): D66 says which losses
  aren't losses; a form backed by client.exe's own evidence (a string, RTTI, a symbol, bytes) may
  land with its losses when the commit names the evidence and each lost address gets an
  `accepted-corrections.json` entry (`"decision": "D240"`, `moved_to` null) until regained; any
  other loss waits for the user before the commit.
- Edit the source; describe each E&B change to an EA-derived file in its end-of-file `// EnB:`
  block (conventions.md), never inline above code. A new reconstructed file gets its description
  (`RECONSTRUCTED`) in its ledger shard: `tools/vc6/ledger.py describe`. Scripted edits go in a script saved in `.work/`, not an inline heredoc
  (escapes get mangled).
- Generated files (`docs/imports.md`, `coverage.md`, `app-inventory.md`, `docs/data/*`) are
  regenerated by tools; never hand-edit them.
- Build VMs come from the pool (`python tools/vc6/pool.py lease|release`, or
  `verify.py --pool K`), addressed by IP (clones share a computer name); release what
  you lease, never use the base image. After a VM restart run `python tools/vc6/vc6.py discover`.
- Inline assembly stays wherever the client has it, with a C-equivalent comment (D70).
- Safety (D69): never a modal dialog (`-nomsgbox`) unless you have way to pass input and respond to 
  the dialog yourself; full screen is fine; no screen grabs, images only from a program's own back buffer;
  never the game's install folder as working directory, and never write into it (reading it in place and 
  copying from it are fine, D143); no registry changes except as stated by D181 or to keys in client.exe; 
  never push `master` (the coordinator pushes only its run branch and opens a PR, D148,
  D157; builders never push); `git add` by name (never stage `.claude/settings.json`: tracked, the
  maintainer changes it).
- Decisions are the user's (D1, D2...). Propose with a recommendation; don't decide silently.

## Reverse-engineering tools: pick in this order
1. Existing project data: `docs/data/symbols.json`, `class-methods.txt`, `rtti.txt`, bytematch reports.
2. `tools/re/*.py` (byte matching, gaps, vtables, layout) before writing a new script. All of
   them use verified function starts by default (D27). Instruction-level questions:
   `tools/re/client.py dis|name|refs|callers` (seconds, names resolved). Vtables:
   `vtables.py --objs build/<lib>/obj --class C --list`, with `--seed C=ADDR` when C's own code
   doesn't match yet.
3. Pseudocode: `python tools/re/pseudocode.py --show ADDR` prints Ghidra's saved output from
   `.work/pseudo/` (every function not yet byte-exact, vtable-only ones included). Missing (fresh
   clone)? `python tools/re/pseudocode.py` rebuilds it (~4 min analysis the first time, then ~80 s).
   After `symbols.json` gains names, refresh with `pseudocode.py --all` (every function, exact ones included,
   in place), then `--check`. Never delete `.work/pseudo/`: a plain run skips exact functions, so their files
   (triage.py's and appfile.py's input) would be lost.
4. REA MCP server (`mcp__rea__*`) only when the saved pseudocode isn't enough (xrefs, call graphs,
   interactive questions). Its first request in a session runs Ghidra's full analysis of
   client.exe: about 5 minutes, every session (the project is discarded on close; a `close_binary`
   snapshot only caches answers already given, not the analysis: tested 2026-10-23). So open it
   early and keep working with `client.py` meanwhile; batch addresses into one `batch_decompile`.
   Don't spend calls on `set_addresses_names`: names are lost on close. Record confirmed
   addresses in docs (and `symbols.json` via `symbols.py`), not in REA or just the chat.

## Keeping context small (rules, same weight as the hard rules)
- These always go to a log, and only the summary is printed: `verify.py` (the per-library
  totals line), `pairs_cmp.py` (category counts; entries only for a non-empty category, at most 20),
  `build.py`, harness runs, `client.py callers|refs`, and any `grep -r` over `app/`, `tests/` or
  `docs/` (run `-c` or `-l` first). Pattern: `cmd > .work/log/<name>.log 2>&1; tail -20 .work/log/<name>.log`.
- Any other command whose output size you don't know: same pattern, or `| head -40`. Long jobs
  (`bytematch_all.sh` ~4 min, `verify.py` ~50 s): run once, don't loop.
- Reads: `grep -n` to find the place, then Read with offset/limit (at most ~150 lines). Never read
  progress.md, workflow.md or conventions.md whole.
- Images cost the most: one back-buffer shot per check (the one that answers the question), never a
  run's whole set.
- Delegate when a question needs a third search, a fourth file, or any digging through logs,
  transcripts or git history: give it to a subagent (Explore for code, general-purpose for logs;
  `docs/builders.md` §4 for builders' models) and keep only its conclusion.
- One item per session: when a PR merges or an item lands, offer `/handoff` and a fresh session
  before starting the next item.

## Handoff target
Prepend a dated entry to the Log in `docs/progress.md` (newest first). Add new traps to
`docs/workflow.md` §3 (builders put them in their report; the coordinator files them). Update
decisions/open lists in place. Do not append a second status doc. progress.md §4 (Next steps) holds
open work only: delete an item when it lands, never mark it done (its history goes in the log entry).

## Commits
Imperative sentence subject stating the evidence/gain (see `git log`). Commit when asked or when
the agreed plan says so. End the message with the `Co-Authored-By` line your harness gives you
(D71: it names the model that wrote the commit). Pushing: D148 (run branches and PRs only, never `master`).
