The exact6A1C90 source witness
----------------------------
The checked-in source performs three member normalizations. Its last relevant
sequence is a real new direction derived from a matrix-rotated offset:

  Vector3 light;
  Unknown_Rotate_Vector(tm, Unknown1D4, &light);
  dir = light + dir;
  dir.Normalize();
  RCamera->Set_Spot_Direction(-dir);

The function is in_tree exact, and attempts.csv records an exact result on
2026-11-05 12:35, after the alias-free rotation helper was recovered. This is
checked-in exact-function evidence; this audit did NOT freshly compile6A1C90.
Its normalization operation is the member API, not free Normalize. No type
name or source-owner attribution was inferred from a shared helper pair.

Retail6A1F31..59 calculates a single emitted squared length.6A1F5D compares
against zero,6A1F68 branches on equality, and6A1F71 calls Inv_Sqrt with the
stored length. Then:

  006A1F76 fstp dword ptr [esp+8]
  006A1F7A fld  dword ptr [esp+2c]
  006A1F7E fmul dword ptr [esp+8]
  006A1F82 fld  dword ptr [esp+30]
  006A1F86 fmul dword ptr [esp+8]
  006A1F8A fstp dword ptr [esp+24]
  006A1F8E fld  dword ptr [esp+34]
  006A1F92 fmul dword ptr [esp+8]

The current member source computes len2=Length2(), tests len2!=0, then spells
Inv_Sqrt(Length2()). The exact caller proves that VC6 can common those two
source evaluations into one emitted calculation. Thus one emitted Length2
does NOT distinguish the free API from the member API. The earlier general
workflow heuristic is insufficient when the compiler can common the expression.

The member API also provides the actual source boundary for a float inverse
which is popped to memory before the component products. This matters because
the former candidate kept the extended-precision inverse on the x87 stack for
its first product. Merely commuting multiplication or asserting mathematical
equivalence would not prove the same machine behavior. The native results and
literal comparisons below, rather than algebraic reasoning, decide the test.
