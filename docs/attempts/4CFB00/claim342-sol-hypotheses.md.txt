## Batch 1: child guard and break control flow

The earlier `both_guard` changes second child and factory checks, not both
child checks. Both child positive guards with an explicit factory return is a
distinct valid shape. Retail's first and second child failures share right
cleanup at 0x4CFB49; factory failure has a separate right cleanup at 0x4CFCA4,
and those two paths share the left cleanup at 0x4CFCC9. Success uses a separate
right cleanup and out-of-line left destructor. Nested child guards may let VC6
share only child failure while preserving factory return and success exit.

The earlier reports mention do/break, but all actual tested sources were
inspected and none contains it. A single-iteration do scope with breaks on only
the two child failures gives an explicit common lexical failure destination,
while factory failure remains a function return. Both RefCountPtr locals stay
outside the scope, constructed left then right before the first Accept, and
destroyed right then left with the same exception predecessors. No callback,
string temporary, ownership operation or reporting assert changes. These are
two purposeful CFG forms, not an instruction-level spelling sweep. Compare
actual cleanup edges, calls, frame and EH in both specializations.

Batch 1 actual results: sol_int_child_guards is 728/728 bytes, residue53/50;
sol_int_child_break is 721/721 bytes, residue106/103. Both preserve267 original
pairs/symbols with no gains. Both child checks jump to final common normal
cleanup, unlike retail first-failure backward edge; both still inline base ctor
and final left destructor,22 calls vs24. Thus source nesting shares the child
exit but not the required initial cleanup. Child guards improve the old
second-guard base but do not beat concurrent float Sol's clean45/42 helper form.
The do/break output is distinct, not a prior shortcircuit duplicate.

## Batch 2: const string subscript's address

Root approved this distinct actual helper mechanism after reviewing the lead.
Canonical VC6 XSTRING:335-340 const operator[](size_type) checks `_Ptr == 0`,
returns `*_Nullstr()` in that case, otherwise `_Ptr[_P0]`. Get_Token returns
const ExprMathTokenClass&, so Text selects this const overload, with no freeze,
write, allocation or bounds exception. At index zero the address is exactly the
same `_Nullstr()` or `_Ptr` as c_str(), retaining its null termination including
the empty string and embedded-NUL truncation. c_str() instead returns a ternary
pointer, whereas subscript returns a reference through explicit if/else. Retail
0x4CFBE9 loads the buffer directly then substitutes the singleton on null,
whereas every prior form initializes the singleton then conditionally overwrites
it. A real reference-return helper can change this lowering and nested inline
budget; data() was only a forwarding call and produced no change. Probe just
original and second-guard bases, then inspect actual string instructions and
missing calls rather than sweeping positions.

Batch 2 actual results: original864/858 bytes,residue81/81; guard816/810 bytes,
residue49/49. All267 original pairs/symbols preserved; no exact. The guard
restores the retail base constructor call without changing direct null compares
or materializing a bool, although string select remains the singleton-first
sequence. Final left destructor remains inline. This is a complementary real
helper effect to float Sol's operator* Is_Constant (which restores final left
destructor while leaving base ctor inline), supporting one targeted composition.

## Batch 3: scoped named string lifetime

Root approved this actual lifetime mechanism after confirming earlier named
text inputs name only a const char*, not std::string. Construct the named string
from the same c_str() inside a lexical block containing only factory assignment.
The returned PtrType temporary is destroyed at the factory-assignment semicolon,
then the named string at block close, immediately before the factory-null test.
This preserves retail's order (PtrType temp state3 -> string state2 -> local
state1), the C-string truncation semantics and callback/factory order. The named
object versus full-expression temporary is a documented VC6 lowering lever
(workflow.md 3.2: std::string s(x); v.push_back(s) != v.push_back(string(x))).
It may explain changed string scheduling and function-wide cleanup factoring.
Probe just original and guarded bases, no extended string lifetime or string copy.
