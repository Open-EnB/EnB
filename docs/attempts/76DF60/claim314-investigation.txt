## Actual mechanism and falsified predictions

The original object has file-private ret at .bss+0 and b1 at .bss+2, with section size 3 and flags 0xC0300080 (4-byte alignment). Its final ret load is a dword read at object 0x1F7. Retail b1 is 0xBE82DC and ret is 0xBE82DE, so retail ret is only 2-byte aligned. The ordinary linkage tests below preserve the original storage offsets and do not change that read. The prediction that making b1 external would force declaration-order allocation was falsified by the actual object.

Root then supplied a distinct initialization/storage hypothesis: the existing initialized code_mask has 26 bytes, so explicit zero initialization might place ret after it at a word-aligned offset in initialized .data. The experiment succeeds, but that particular .data-placement prediction is also falsified. VC6 still emits ret in uninitialized .bss; explicit initialization changes allocation to b1+0, ret+2, section size 4 and the same 4-byte section alignment. This is now the retail relative layout. The actual generated final read becomes `mov cx, word ptr [ret]` (`66 8B 0D`), with the extra operand-size prefix restoring the missing byte. No source padding was introduced; the compiler naturally leaves one byte between the real byte and real word. The initialized .data sections remain byte-for-byte unchanged.

This is evidence for a real initialization and storage-emission mechanism, rather than proof of every internal step of VC6's optimizer. It is consistent with the compiler widening a word read when its fixed symbol is known 4-byte aligned, and retaining the word read after the symbol becomes 2 mod 4. A full linked-image address/layout comparison has not been performed.
