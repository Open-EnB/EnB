## 0x578350: geometry and x87 lifetime

Retail loads bounding extent Y once following virtual slot +0xF4, loads pos.Y, computes the lower integer while leaving height on the x87 stack, converts Width+pos.X, then uses `fadd [pos.Y]` destructively on the surviving height before the top conversion. Baseline instead loads pos.Y onto x87 again, adds st(1), and pops unused height after conversion, adding four executable bytes (254 vs 250). Actual diff: runs/baseline/578350-objdiff.txt. Slot, relative operation order and precision must remain faithful. The two 2026-11-11 forms have no surviving individual objects except the L10 source; only the 14 fresh inputs are fully grouped. Ten of those produce the exact baseline raw/masked section; double Y, extent copy/reference and rectangle by-value produce the other four groups, none gains a pair. Precise source and duplicate accounting: 578350/first/forms.json and each replay.json.

The already exact sibling Unknown_30 uses the same position, height, Width and Y arithmetic (with 0.9 multiplier and comparisons); app/client/textgadg.cpp:434-435 calls the same FontSys rectangle operation with pos.Y +/- box.Extent.Y; fontsys.cpp:278-285 uses a copied box and named integer bounds. First-pass named integer bounds, sequential destructive-height assignment, float/double Y/height, AABox copy, extent reference, vector copy, and an actual rectangle layer cover those indicated alternatives. These either reproduce baseline or worsen the exact x87 residue; compiler canonicalization means the source's sequential height mutation was not a solution. Positively unsequenced modification/read across arguments is undefined in C++98, and floats introducing actual intermediate rounding or repeated virtual getter calls are not equivalent evidence. No defensible additional Init candidate has emerged merely from observing a nearby arithmetic spelling. Reopen with evidence of a real operation/lifetime or type convention that changes this specific last-use schedule while preserving getter count, evaluation semantics and x87 precision, not a dead read, padding, fake type, volatile, assembly, pragma or flag.

Considered the separate lifetime of the position result: RenderObjClass::Get_Position is nonvirtual and returns Vector3 by value (ww3d2/rendobj.h:258, rendobj.cpp:490); both retail and baseline pass a stack return buffer, and Vector3 has no destructor. The current value lives for the full use and is never mutated. A const reference to the returned prvalue would extend its temporary through the same scope; there is no evidenced intervening copy, cleanup or changed lifetime to connect it to the last-use height scheduling. A search found no Get_Position-result reference binding in app/client or ww3d2; exact Unknown_30 and related textgadg.cpp:434 use named values. Do not promote a declaration-spelling sweep to a distinct mechanism. Reconsider if a proven nearby compiled accessor/reference case demonstrates different storage or x87 scheduling.

The three distinct cross-function tests altered nesting inside Scroll in exactly the region suspected but outlined smaller sub-operations rather than both Scroll calls. Combining them also did not preserve Unknown_60. There is no supported reason to expect further spellings of these same layers to restore retail's shared actual Scroll call. All-caller and full-context proof remains mandatory.
