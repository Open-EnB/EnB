Retail constructs two empty `RefCountPtr` locals before the first callback,
then checks the left result, assigns left, invokes the right callback and checks
it. At int 0x4CFB49 (corresponding float sequence) the two child failures share
the initial right cleanup; the factory-null path instead has its own cleanup at
0x4CFCA4. The guarded candidate's second failure goes to final normal cleanup,
not back to that first child-failure block. On success retail destroys right
inline and calls the left destructor at 0x4CFDDE; the guard also inlines that
destructor and the constant base constructor. The duplicate second null test
is present in retail and the guarded form, but the c_str buffer/singleton load
order remains different. Its explain class says 23 calls against retail's 24,
with two client-only callees; call counts alone do not identify a complete fix.

The exact unary siblings 0x4CAF50 and 0x4CF7F0 use the existing temporary
`std::string(node->Get_Token().Text.c_str())`; exact `Visit_Leaf` siblings
0x4CB620/0x4CFEC0 use the token string directly for other factory operations.
Exact int/float factories 0x4CBCD0/0x4C7D80 accept const string and smart-pointer
references, and use `Create_NEW` for new nodes. RefCountPtr's destructor
releases then clears; assignment first increments the new referent then releases
the old. Neither delayed destruction, extra owner copies nor callback reordering
is automatically harmless. A whole string copy would retain embedded NUL bytes
where the observed c_str construction truncates; do not substitute it as a
pure spelling variant. `Clear()` by itself does not null the pointer.
