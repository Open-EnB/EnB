## Strongest exact comparator: a real predicate/out-reference operation

HtmlAttributeStackClass::Pop, 0x779F90, symbol
?Pop@HtmlAttributeStackClass@@QAEDPAD0H@Z, 703 bytes:

- Source: /home/dev/Projects/EnB/.work/claim-342/tree/app/client/html/unknown_htmlattrib.cpp:86.
- Object: /home/dev/Projects/EnB/.work/claim-342/global-baseline/729/unknown_htmlattrib.obj.
- Actual inline operation: /home/dev/Projects/EnB/.work/claim-342/tree/libs/wwonline/wlib/dictionary.h:565,
  Dictionary<K,V>::getPointer(const K &, V **) const.
- Full independent existing audit passes: body, relocations/addends, literal
  payloads, handler/FuncInfo, predecessor states, and cleanup funclets.
  Receipt: /home/dev/Projects/EnB/.work/claim-342/astra-research/779F90-audit.json.
  Decoded object/retail and EH: 779F90.txt, reproducible by inspect_evidence.py.

Pop constructs real Wstring k and v before its lookup. getPointer returns C++
bool, assigns its out-pointer only on success, and has internal false returns
for empty table, empty bucket, and missing key. Its inlined false paths target
the caller's first cleanup at 0x77A046 (+0xB6), which destroys v, then k, then
zeros AL. In the successful lookup path the remaining null-node test at
0x77A07E (+0xEE) branches backward to that cleanup. Later no-match paths at
0x77A147 (+0x1B7) and 0x77A170 (+0x1E0) also return there. This is actual
propagation of a meaningful helper's failure results into caller cleanup, not
merely an accessor with an extra inline depth.

Pop's own return type is **bit8, typedef char**, not C++ bool. Its success paths
return a bool local converted to bit8; false paths return FALSE. The success
cleanup destroys the same v/k pair at 0x77A229 and 0x77A237, then copies BL to AL
at 0x77A248 and jumps to the common machine epilogue at 0x77A067. The distinct
return values therefore explain why the failure and success destructor chains
need not merge. This is the principal caveat against Visit_Binary's void return.
Do not call Pop a demonstration that a void visitor will select this layout.

EH predecessors are [-1,0,1,1]. State0 destroys k at [ebp-0x28], state1 destroys
v at [ebp-0x20]. States2/3 destroy two branch-local ArrayList temporaries, both
returning to state1. The failure paths share two genuinely live owners; they are
not constructor-member cleanup or merely loop exits. Its ownership types and
out-of-line destructor costs differ from RefCountPtr and remain another limit.

## Target lifetimes are already supported

eh_check.py independently checked the clean38 candidate's six predecessor/action
maps against BOTH retail targets, including fixed funclet bytes and every
funclet relocation destination/addend. Receipt: target-eh-check.json. Its scope
is the predecessor/action maps and cleanup funclets only: it does not claim
complete handler/FuncInfo parity or unmatched main-body exactness.

The map is [-1,0,1,2,1,1]: left owner; right owner; constructed string temporary;
factory returned owner temporary; allocation cleanup; folded result temporary.
For int, actions are 0xAA7E40/48/50/58/60/6B respectively. Left/right occupy
[ebp-0x24]/[ebp-0x28]. Both owners exist before the first Accept, and each child
and factory operation has the applicable enclosing lifetime in the current
candidate. An owner array/aggregate, deferred right construction, or a by-value
child-result helper would need different lifetime evidence; none was found.

Retail's int second child failure is 0x4CFBB5 -> 0x4CFB49. Initial right cleanup
cross-jumps into the separate factory-failure suffix; normal success instead
inlines right destruction and calls left destruction. The known clean38 code
still duplicates early cleanup, uses the final normal cleanup on second failure,
and is 39 bytes longer. EH agreement does not prove a unique source scope, but
it removes a reason to posit missing owner objects or wrong cleanup actions.
