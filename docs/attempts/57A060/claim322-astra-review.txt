Start from default_accessor. Change only Scroll_To_Selected's outer guard, retaining the original two assignments verbatim:

void UIComboBoxClass::Scroll_To_Selected()
{
    if ((int)Items.size() > NumRows) {
        if (Slider->Is_Enabled()) {
            TopItem = min((unsigned)Selected, Items.size() - NumRows);
            TopItem = Unknown_Clamp(TopItem, 0u, Items.size() - NumRows);

            TopItem = 0;
        }

        TopItem = 0;
    }
}

### Causal prediction and how to falsify it

The documented precedent suggests that nesting can increase a callee's source cost enough to stop its expansion while its standalone optimized code remains unchanged. Applied here, the desired threshold is Scroll inside the already-expanded Toggle copies. If this happens, normal identical-tail merging may produce the same common actual Scroll call already observed in best_both_branches, without changing min/Clamp's standalone implementation.

This is a conditional prediction, not a claim that both outcomes follow. A useful distinguishing observation is an actual Scroll reference replacing the remaining expanded region, together with unchanged standalone helpers. A smaller target, fewer objdiff rows, two unmerged Scroll calls, or an out-of-line Is_Enabled/vector operation is not the predicted result. ### Semantics and reentrancy obligations

The first size query and signed comparison remain first. Slider is read and its virtual slot +0x60 is called only when that comparison succeeds. It is virtual even though the base Is_Enabled body is a simple bit read: do not assume it is pure or incapable of reentrancy.

If the virtual call succeeds, read Selected, Items and NumRows for the original min operation afterward, perform the intermediate TopItem store, then perform the separate original size query and Clamp/store. If it fails, store zero afterward, exactly as before. The outer failed-size path performs one zero store without calling the slider. No cached size, precomputed bounds or field read may be moved across the virtual call.

In particular, `TopItem = 0; if (...) ...` is not this proposal: it exposes a new zero value to the virtual callback and changes the store order. Likewise, caching Items.size(), NumRows, Selected, Slider or the open-combo global before callbacks is not an equivalent implementation for this review.

The target's Owner->Unknown_68(SelectKey) call remains before every Toggle global/state read. Neither nested guard nor any source-line accommodation may change that ordering. No new object lifetime, exception cleanup or EH state is introduced.

## Leads considered but not promoted

- Replace the real Selected read in Scroll with existing Get_Selected(): it is a legitimate accessor, but the present evidence gives no distinct reason for that tiny nested expansion to suppress Scroll rather than move a deeper operation. The getter/accessor cost family and smaller-operation outlining are already well represented. It does not independently justify reopening here.
- Split Toggle's open-global conjunction instead: the same documented cost lever, but it acts on Toggle's cost, risking the already observed failure of outlining the whole Toggle. It is not a second distinct mechanism, and there is no reason to prefer it over changing Scroll directly.
- Make a second Scroll clone or put a different implementation in another holder: this would avoid proving the actual helper/body relationship and would not satisfy the required call identity or source reconstruction. No such workaround is proposed.
- Change min to a macro, force an out-of-line boundary with flags/pragmas, add dead reads, or manufacture state/lifetime work: the real min is a global template, and these routes are contradicted by evidence or excluded by the task.
- Combine the nested guard with earlier wrappers in advance: untested interaction is not itself evidence. Establish the one clean mechanism first, or stop if it fails.
