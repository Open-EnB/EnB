## 3. Running with nobody there (D261)

**How sessions start.** The scheduled tasks `EnB week S0` .. `S7` run
`.work/week-2026-11-17/launcher/start-session.ps1 -Session N`: it stops the previous session's process if it
still runs (one coordinator at a time), then starts `claude --model opus --permission-mode auto --remote-control
EnB-S<N>` in its own console with a one-line prompt that points here. Its log is
`.work/week-2026-11-17/launcher/launcher.log`. A session that is late with its handoff is therefore killed at the
next start: keep the handoff times.

**No question is ever asked.** No AskUserQuestion, no "shall I". An item that needs the user is parked with one
line under "For the user" (below) and the next item starts.

**Recovery, the first step of every session** (before `run_branch.py start`):
1. Read the newest log entry of progress.md and the tail of the launcher log. If the session before wrote no
   handoff entry (it was cut off or killed): read its plan log (`.work/run-<date>/plan.md`), list its worktrees
   (`python tools/vc6/wt.py list`), give the finished ones to a lander, park the unfinished with their state in
   the plan log, and write the missing log entry yourself, marked "written by session N from the plan log".
2. `python tools/vc6/pool.py list`: release leases of agents that no longer run (stale importer leases held VMs
   for five hours on 2026-11-16), then `pool.py stop-idle --minutes 0`.
3. The heartbeat (`pacing.py heartbeat`) for HEAD's health, memory and the meter. If the meter is already at or
   past this session's cap, do the PR step below, write a three-line log entry and stop.

**Branches, PRs and merging** (D261 relaxes D148 until the user's return; one `gh pr list` per session start and
per handoff, no polling in between):
- The coordinator **merges** (`gh pr merge --merge`) a run PR of this week, and the plan's PR, once the
  required check `vc6-verify` and the hosted checks are green on its head **without anyone's comment**: the
  service passed it by itself, so nothing was lost outright and nothing that runs on the host changed. Then
  `run_branch.py cleanup`.
- A PR that waits for `/verify-approved SHA` (it changes tools: most crediting work does) or `/accept-d66 SHA`
  is the user's: agents never post those commands. Put the exact comment to post at the top of the PR's summary,
  then **freeze the PR** (no further push: a push voids the approval). Once the user has commented and the
  service shows green, the next session merges it, oldest first.
- A session starts its run branch from origin/master when nothing is frozen (`python tools/run_branch.py
  start`), otherwise **stacked on the newest frozen run branch**: `git branch run/<date> run/<frozen>`, then
  `run_branch.py start --date <date>`. Never wait for a merge.
- Past D246's valve a branch is parked, as always.

**For the user.** Each handoff's PR summary (`run_branch.py ready --summary`) begins with a section "For the
user": the comment to post if one is needed, the decisions parked for §3, anything that stopped. That section
and the log entry are the only channel; the user may also open the session `EnB-S<N>` in the Claude app
(Remote Control) and type into it: such a message is the user's and outranks this plan.

**Things that would stop the week, and what to do:** a 429 or a usage cap: the session waits by itself; the
next session's recovery picks up. Host memory: the heartbeat's allowance, never more than four builders with
VMs. A restart of the host: nothing starts again until the user logs on; nothing to do. HEAD unhealthy at a
session's start (verify loses pairs against the baseline): the session's first item is to find the landing
that did it and revert it on the run branch.
