# From a packet to the object model: how the client's objects are created, updated and removed

Mapped 2026-10-28 (PF1) from client.exe, the app tree and the saved pseudocode. It starts where
[kernel-map.md](kernel-map.md) §5 ends (a datagram -> the opcode factory 0x869790 -> a
`XxxPacketClass` queued on SClient's connection) and follows the packet into the objects. The AUX_DATA
decode itself is in [decode-path.md](decode-path.md); the client base and SClient in
[kernel-map-step9.md](kernel-map-step9.md) §2. Names are the client's where it has them (asserts,
profile labels, RTTI), the tree's `// NAME` names otherwise; *guess* marks a reading without proof.
Rebuild states are as of HEAD 2205fd2: **exact** = in `docs/data/imports.json` `in_tree`; **NOT EXACT**
= in the tree with a `// NOT EXACT:` marker (its class); **not rebuilt** = no tree code (`attempts.csv`
rows in brackets). The per-opcode table was generated by `.work/pf1/handlers.py` (vtable slot +0x08 of
each class in `docs/data/packet-factory.txt`, through the incremental thunks).

**Recap of kernel-map.md §5.** The CordMgr / TCP tasks read datagrams; the factory builds one packet
object per message (`PacketClass`, vtable 0xAEDE88: +0x04 the connection, slot +0x08
`Process_Packet(void *)`) and queues it on a peek connection. Nothing in the object model runs there.

## 1. The dispatch

**There is no opcode table or switch on the receive side.** The only switch on the opcode is the
factory's (pk.cpp 0x869790); after it, dispatch is the C++ virtual call `packet->Process_Packet(this)`,
slot +0x08 of each packet class's own vtable. So the handler for an opcode is "slot +0x08 of the vtable
the factory's case stores", and the handler's file is where that function was compiled:

| Where the slot +0x08 bodies live | Count | What they do |
|---|---|---|
| app\client\cpacket.cpp, 0x7333B0-0x73F680 | 107 opcodes (kernel-map.md counts 99 classes and 109 functions with the helpers) | the server -> client handlers: they cast the argument to `SClient *` (or `ClientClass *`, some through ClientClass slot +0x18, which SClient answers with `this`) |
| app\packets\clientstub.cpp | 149 (the remaining opcodes of the 263) | client -> server packets (TURN 18, TILT 19, MOVE 20, ...): a 0x19-byte `assert; return true` |
| app\client\tasks\tsk_login.cpp | 6 (1, 111, 112, 117, 118, 120) | the login task's packets (VERSION_RESPONSE, GLOBAL_TICKET, GLOBAL_AVATAR_LIST, GLOBAL_ERROR, ...), all exact |
| app\client\tasks\tsk_game.cpp | 1 (54 SERVER_REDIRECT 0x766FC0, exact) | the redirect to another sector |
| (PacketClass's base 0x52B240, asserts) | 0 | kernel-map.md §5 counts 32-34 here; their factory vtables (0xB09760, 0xB09724, 0xB096E8) hold cpacket.cpp's message-line handlers 0x736A20 / 0x736AE0 / 0x736BA0 (107 + 149 + 6 + 1 = 263) |

**Who calls it, on which thread.** Everything below runs on the main thread inside the kernel's task
loop (kernel-map.md §1-§3); no network thread touches the objects:

```
ClientTask::Run 0x766630 -> MODE_SECTOR 0x766BD0
  -> SClient::Do_Frame 0x742B60 (ClientClass slot +0x14; returns 0..5 to the task)
       1. unless the byte +0x1198 is set: the player root [+0x12C0] slot +0x20, then for every object
          in ObjectList: object slot +0x1C 0x6F5120 = AuxData->Unknown_20 (ages the change marks, §2.4)
       2. +0x10BC = Unknown_Get_Ticks()            (the client clock the positional states read)
       3. the input queue (0x42EDB0, 0x42EA80, inpdsp 0x429A20, the key handler 0x7436A0)
       4. this->Process_Packets() (slot +0x0C, call at 0x742F25) = SClient::Process_Packets 0x7427C0:
            while ((p = Connection->Peek()) != 0) {      // Connection = ClientClass +0x1124
                if (!p->Process_Packet(this)) return;    // false: stays queued for the next frame
                delete Connection->Receive();
            }
       5. 0x75B320; unless +0x1198: Process_AI 0x744260 (every object's slot +0x20, the per-frame
          update, §2.5; finished effects and expired +0x86C records deleted), then the views
  ClientTask's Render -> SClient slot +0x64 0x744690 (draws what step 5 placed)
```

Every rebuilt handler returns true (none keeps its packet). The owner of the packets in flight is the
connection at ClientClass +0x1124 (a peek connection over a statistics wrapper, kernel-map-step9.md
§2.1); a handler never deletes its packet. The login task and tsk_game read their own connections (not
traced, kernel-map.md §5's open list).

## 2. The object model

### 2.1 The client base's tables (app\client\client.cpp; client.h's `ClientClass`)

SClient (0x14F8 bytes) starts with the client base (0x1150 bytes, constructor 0x726100 NOT EXACT,
vtable 0xB02D7C). It holds four wwlib `HashListClass` tables of 0x428 bytes (a GenericList head + 257
buckets + two counts), each keyed by an id modulo 257:

| Offset | Table | Record | Key (node +0x14) | Add / Remove / Find |
|---|---|---|---|---|
| +0x1C | `ObjectList` (the client's name: assert `ObjectList.Find(object->Get_Game_ID())`, l.222) | `ClientObjectClass`, node at object +0x60 | the game id | slot +0x40 `Add_Object` 0x7274D0 (exact), +0x44 `Remove_Object` 0x727600 (NOT EXACT shape), `Find_Object(unsigned)` 0x727070 (NOT EXACT shape; 99 callers), `Find_Object(const char *)` 0x727130 |
| +0x444 | `EffectList` | `EffectObjectClass` (eff_o.cpp), node at +0x04 | effect id (+0x30) | +0x48 `Add_Effect` 0x727780, +0x4C `Remove_Effects` 0x7278F0, +0x50 `Get_Effect` 0x727AD0, `Find_Effect` 0x7273F0 |
| +0x86C | `Unknown86CList` | `Unknown86CRecordClass` (CREATE's type 10: influence.cpp's 0xB8-byte object, 0x7E87C0) | +0x24 | +0x54 0x727B40, +0x58 0x727CA0, `Find_Unknown86C` 0x727460 |
| +0xC94 | `Unknown831340List` | the item templates (0x60 bytes, ctor 0x831340; 'Null Item' at construction) | the item template id | ITEM_BASE 37 adds them |

`Find_Object(id)` hashes; on a miss it walks the whole list and asserts (l.165) if an object with that
id is there anyway, then returns 0: the list walk is a consistency check, not a second lookup.
`Add_Object` sets the node's key from `Get_Game_ID()` (+0x90), adds it and sets `ObjectsChanged`
(+0x1140; `Get_Objects_Changed` 0x728430 reads and clears it). The list is walked through its head at
+0x24 (record at node +0x10).

Members the handlers use besides the tables: +0x10BC the client clock (ms ticks, set each frame),
+0x10C0 an `__int64` server time base (a `DurationClass`; packets' TimeStamps are rebased by it;
SERVER_HANDOFF 58 and CLIENT_SET_TIME 52 set it), +0x10C8 / +0x10CC (32) / +0x10D0 a running average of
the positional packets' lag over 32 samples and their count (0x728180 resynchronises when |average| >
50 after 64 samples), +0x10D4..+0x10E8 the sector's z band and box (SET_ZBAND 42, SET_BBOX 43),
+0x10EC..+0x110C SERVER_PARAMETERS 66, **+0x112C the player's own object id** (tree name
`AvatarID`, D123; CLIENT_AVATAR 55 sets it from the packet's AvatarID),
+0x1130 `ShipID` (CLIENT_SHIP 71), +0x113C a counter CREATE's type 10 decrements for its record id.
SClient adds +0x12C0 the player's aux root (DeltaPlayerClass, 0x752510), +0x12C4 the player-variable
roots (PLAYER_VAR_AUX_DATA 28), +0x1334 / +0x1338 the decal and colorization INIs, the views (MainView,
the camera manager, the chat panel).

### 2.3 Creation, lookup, removal

* **Created** only by CREATE 4 (0x733700, §4 has the sequence): `new` by type, the constructor, the
  model from the base asset (0x6F5140 in co.cpp, 20 callers: `(BaseAsset, client, Scale, &HSV)` ->
  RenderObjClass, assert `robj`; type 8 gets a `LightClass` instead), `Set_Model` 0x6F33F0 (releases the
  old model, stores +0xA4 / +0xA8 / +0xAC, tells the lego object through its slot +0x20), slot +0x04
  (attachment points), then `Add_Object`. Type 10 also makes an influence record (0x7E87C0) for the
  +0x86C table and swaps the model for a `Null3DObjClass("NULL")`. CHANGE_BASE_ASSET 38 (0x737400)
  reuses 0x6F5140 + 0x6F33F0 on an existing object.
* **Found** by `Find_Object(GameID)` in nearly every handler; `Get_Ship()` (slot +0x30, `ShipID`) and
  `Get_Avatar()` (slot +0x28, `AvatarID` +0x112C) are Find_Object on the two remembered ids.
* **Updated** in three ways: the AUX tree (§2.4), the positional state at +0x98 (§2.5), and direct
  calls on the object or its model (decals, colorization, render states, name decal, attachments,
  targets, relationship: the table in §3).
* **Removed** by REMOVE 7 (0x7362F0, exact): SClient's 0x74C530(GameID) unless 0x744B60 (*guess*: the
  target / selection UI forgets it), `Find_Object`, `Remove_Object`, `object->Unknown_08()` (0x725120:
  every attached child is detached, removed from the client and deleted), `delete object` (0x6F2FE0:
  co_data.cpp's `Remove_All` 0x79D390 for the per-object records, the sounds, the lego object, the
  model). REMOVE leaves the +0x86C record alone: Process_AI deletes it once its slot +0x08 says so. The
  client's destructor 0x726C60 deletes whatever is left in all four tables.

### 2.4 Where the aux data attaches, and how a delta reaches the object

The constructor stores `AuxData = UnknownCOClass::Unknown_Create_Aux_Root(type, game_id)` (0x6F6000,
aux_roots.cpp, generated): types 0/1 DeltaShipClass, 3 Planet, 4 Component, 8 Light, 11 Stargate, 12
Starbase, 25 Hulk, 34/37/41 Decoration, 38 Harvestable, 39 ManufacturingLab; **any other type has no
aux root** (AuxData 0; the accessors' `FAIL_IF(!aux_data)`). The player's own root is SClient +0x12C0.

AUX_DATA 27 (0x7364C0): GameID 0 -> `[sclient+0x12C0]->Decode(...)`; else `Find_Object(GameID)` ->
`((DeltaCompoundClass *)object->AuxData)->Decode(LinearBufferClass(Data, Size, 0x400, false),
DurationClass(+0x10C0))` (0x4A3FA0 exact; the record or tree codec and the leaves as in
[decode-path.md](decode-path.md)). Each leaf's Read (slot +0x2C) stores the value at **leaf +0x84**
(`DeltaTemplateClass<T>`), then slot +0x3C (0x4A4F20) marks it.

**The change mark** (`DeltaClass +0x70`, delta.cpp, exact): 0 = default / cleared (slot +0x1C), 2 =
changed (slot +0x18, and +0x3C after a Read, which also marks every parent up the chain), 1 = set,
seen. Each frame, **before** Process_Packets, Do_Frame calls every object's slot +0x1C 0x6F5120 ->
`AuxData->Unknown_20()` (0x4A53A0 / 0x4A4DF0): every 2 becomes 1, descending only into changed
compounds. So between the packets and the next frame's age step, `mark > 1` means "changed this
frame", and that is how a delta reaches the object: **the object does not get a callback; its update
reads the leaves it cares about and tests their marks**. Two forms:
* fixed offsets into the root, e.g. 0x6FC9A0 (lights, type 8, called from slot +0x20): `if (aux[leaf
  +0x70] > 1) model field = aux[leaf +0x84]` for the light's colours, intensity and attenuation;
* by name: `NameClass("EngineThrustState")` + 0x514B60 (find a child by name) in 0x6F4610, and co.cpp's
  accessors (`CombatLevel` 0x6FF330, `PercentFull` 0x6FF1D0, guild / name 0x6FFC80 -> 0x6FF7A0, IsOrganic,
  IsInPVP ...).

The interpolated leaves (delta_interpolator.cpp, slot +0x3C override 0x4A68E0) are the one case where
decoding itself does more than store.

### 2.6 The proximity system (app\shared\px*.cpp)

A sweep and prune over axis-aligned boxes (PX1, 2026-10-28; px.cpp 0x44B760-0x44D740 and px_wrapper.cpp
0x4560B0-0x457740 are rebuilt). **PxList** (`ClientClass::Px` at +0x08, made in the constructor 0x726100 beside
the PxProcessClass at +0x0C) keeps three sorted, doubly linked lists of box ends, one per axis; it is their
sentinel. A **PxBox** has a low and a high end and a filter: it is told about another box b (`On_Enter(b)` /
`On_Exit(b)`, vtable slots +0x04 / +0x08) only when `(b->Self & Mask) == Test`. `PxList::Insert` links a box's
ends and reports every box it overlaps; `Remove` reports the overlaps ending; `Set_Corners` walks each moved end
past its neighbours, so a frame's cost is the number of ends crossed, and reports each newly overlapping or
separated box once (the static `Notified` vector); `Set_Self` / `Set_Test_Mask` report the boxes whose filter
result flips.

**PxWrapper** (a `DynObj`'s ProximityObject, type 24's base at +0x188) keeps: the `PxObject` (its owner, the
last position and radius), three boxes, its `PxList` (`List`, NULL while not inserted), three flags and a vector
of `PxCallback`s. The **tight box** (Self 3) is the radius / sqrt(3) cube around the position (the cube inside the
sphere), the **loose box** (Self 5, Test 0x1D, Mask 0x15; a `PxPollCallback` whose overlaps go to
`_Collision_Callback`, which hands each pair once, lower address first, to px_collision.cpp's
`PxCollision::Process`) the radius cube (the cube around the sphere), the **callback box** (Test 5, Mask 5; in
the list only while flag +0x0D is set; a `PxOwnerList` collecting the overlapping boxes' DynObjs) takes the corners `DynObj::Update_Avoidance(low, high)` gives it. Flag
+0x0C flips bit 8 of the loose box's Self and Mask, flag +0x0E (set by the constructor) bit 0x10 of the loose and
tight boxes' filters.

**Per frame** `DynObj::Update_Proximity` 0x44B090 passes the object's position (its slot +0x24) and radius
(+0x04, type 24's slot +0x34 sets it) to `PxWrapper::Update` 0x456B60, which ignores changes under 0.1, moves the
loose and tight boxes (`PxList::Set_Corners` when in a list) and then calls every callback's slot +0x10;
`Update_Avoidance` 0x44B150 sets the callback box's corners (0x456900, also under 0.1 ignored). **No caller is
known**: client.py finds no call or pointer reference to Update_Proximity, Update_Avoidance, fp_tt.cpp's
0x449EA0 (the other caller of 0x456900) or `PxWrapper::Add_To_List` 0x456660, the only way a wrapper enters
the list. So in the retail client the wrappers and boxes are built and kept, but (as far as the references
show) never inserted into ClientClass's PxList nor updated: *guess*: the proximity / avoidance code is dormant,
or reached through a path not yet found (a vtable of an unrebuilt class would show as a pointer reference).

**Callbacks.** `PxWrapper::Unknown_456F60` / `Unknown_457190` take a factory's `PxCallback` (vtable 0xAE7B28:
Clone, Attach, Detach, Update, Add_Filter). The type bits pick the class: Accurate (1) a `PxAccurateCallback`
subclass, Liberal (2) / Conservative (4) a `PxBoxCallback` with the radius (or radius / sqrt(3)) as its extent; with
Polling (8) the polling classes instead (`PxPollAccurateCallback`'s sphere for Accurate, `PxPollCallback`
otherwise). Every callback reports `function(own DynObj, other DynObj, PxCallbackEvent)`: `PxBoxCallback` from
its box's On_Enter / On_Exit (Enter / Exit), the polling and accurate ones from their `PxProcessNode::Process`
(Update for polling; Enter / Exit on a change of the accurate test). A polling or accurate callback with something

### 2.7 What the main view reads of the object model (app\client\mainview.cpp)

The main view (SClient +0x1358, MainViewClass) never owns objects: `SClient::Add_Object` / `Remove_Object` tell it
(0x514270 / 0x514390: the object's model into its +0x10C scene unless 0x6F5D90 says no), and every frame it reads
(MV2, 2026-10-28):

* **The target, from the avatar's aux data** (`Unknown_512400`, slot +0x14 0x5129D0 every frame): the avatar is
  `Get_Avatar()` (ClientClass slot +0x28, `Find_Object(AvatarID)`); its aux data's `TargetGameID` (an int delta,
  read only when its +0x70 is set) is the server's target. When it differs from the scanner's (`Cpit->Scan`'s
  +0x88, an object pointer) the main view looks it up with `Find_Object` and hands the object (or NULL) with the
  `TargetThreat` / `TargetThreatSound` strings and `TargetThreatLevel` to the chat panel (0x563910: its game id
  when 0x6F5A40 says so), the radar (0x7BD6E0) and the scanner (0x60E540). A `TargetGameID` set twice (+0x70
  above 1) clears the star map's +0x10. So the target travels as aux data (AUX_DATA 27 into the avatar's
  DeltaPlayerClass), not as a pointer, and the scanner's +0x88 is the view's copy (slot +0x5C 0x5136D0 returns
  it; SClient 0x744E70 sends it as ACTION 44).
* **The camera and the orbitals, not objects** (`Update` 0x50F1B0): the sun, fog and ambient colours of
  OrbitalManager (+0x140, updated from the client clock +0x10BC / +0x10C0 in hours) go to the three scenes and
  the land's lighting; view mode 0 (space) places the four lights around the sun and the camera's Z axis. Only
  the land reads the camera (Update_Patches).
* **Picking** (slot +0x60 0x512BB0, not rebuilt): the screen point through the view's IntersectionClass
  (+0x88) against render objects; how the hit maps back to a ClientObjectClass is still to be read.
