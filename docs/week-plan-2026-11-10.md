# Week plan, 2026-11-10 to 2026-11-17: the Fable reset week

The session layout and the coordinator prompts for the usage week of Tuesday 2026-11-10 12:00 to Tuesday
2026-11-17 12:00 PST (D225). Each session's coordinator reads its own row and prompt here, nothing else of this
file. The log entries of the week record what happened; this file is not updated with results, only with a
changed plan (targets or themes the user moves at a review).

## 1. The budget

- The user spends one Fable usage reset this week. Fable is capped at 50 % of the weekly limit; the reset
  subtracts the Fable usage from the meter (it does not zero it). So the week holds about 150 points: 50 on
  Fable, then 100 on Opus and lower models.
- 3 points were spent before this plan (the tools sessions of 2026-11-10, on Fable: they count toward the 50).
- **Phase A, sessions 1-4:** coordinator and reasoning builders on Fable until Fable's 50 are spent (about 47
  left, about 12 a session). The user applies the reset at the review after session 4.
- **Phase B, sessions 5-14:** coordinator and builders on Opus, landers and mechanical work on Sonnet, about 10
  points a session, 100 by Tuesday 11:30.
- Subscription only all week: no agy builders, no API-key builders, no Batch API round.

## 2. Which work goes to which model

D93 (2026-10-27) compared Opus, Sonnet and Haiku builders, not Fable: the stronger model won clearly on the
reasoning-heavy file (B-opus +86 pairs against Sonnet's +36 for more tokens) and tied on the routine one. The
only Fable builder figure is 2026-10-29's: about 1.1 % of the week per Fable round. This plan extends D93's
result one level up without a measuring run:

| Work | Phase A | Phase B |
|---|---|---|
| Coordinator | Fable | Opus |
| Analysis whose answer steers many builder runs (the map, class layouts, shared headers, the library classification) | Fable | Opus, only what phase A left |
| First drafts of unexplored files from pseudocode | Fable, two verify rounds per function, then NOT EXACT with the best form stashed | Opus |
| Stuck functions: §4 item 7's queue, item 10's parked leftovers, near misses | Fable, D89's count limits lifted | Opus under D89 |
| Finishing drafts to exact, routine verify loops, new files of a known pattern (packets, windows like their neighbours) | Opus | Opus |
| Landing (lander), harness and POC checks (checker), filing reports into docs (doc-filer), generator reruns, log digging | Sonnet | Sonnet |

Rules that hold in both phases: D89's ban on register-only and order-only residues; every other rule of
`docs/builders.md` §2; proposals instead of decisions.

Split of the week's points, as a guide: about 60 % new app code, 15 % stuck work, 15 % quality, 10 % libraries
and tools.

**The known risk** is phase B's rate: 10 points a session needs the coordinator and about four Opus builders
running the whole time, and four is where host memory capped the allowance on 2026-11-10. Sessions 5 and 6
report their points per hour; if they fall short, the user decides at Saturday's review whether a second batch
of Fable builders (not refunded) takes the stuck and quality work late in the week.

**If the Fable limit stops a phase A coordinator** before its handoff, the user restarts the session on Opus
with the same prompt; the plan log and the run branch carry the state.

## 4. The week's shared state

- The run branch and PR per session, as the coordinator-pacing skill says (`python tools/run_branch.py start`).
- **The queue:** `.work/week-2026-11-10/queue.md`, written by session 1 from `docs/data/triage.json`
  (`triage.py plan`), the pseudocode and the callers: one row per proposed file or class (address range,
  function count, callers into it, the subsystem, what it unlocks, state: open / drafted / exact / parked).
  Every later session takes its items from the top, marks rows as it goes and names the next ten in its handoff.
- **Rates for pacing.py in phase A** (assumed until the first heartbeat lines correct them, since the script
  scales both to the burn observed): `--coordinator-rate 1.2 --weekly-rate 0.3`. Phase B uses the defaults.
- Each handoff's log entry reports, besides the usual: points of the week per hour by phase of the night, pairs
  gained per point, the builders by model with their tokens, and the meter at the drain against the floor.
